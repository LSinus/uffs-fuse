# UFFS FUSE Bridge
A FUSE (Filesystem in Userspace) bridge for mounting UFFS (Ultra-low-cost Flash File System) images on macOS and Linux.
This project allows you to natively mount, read, and write to raw `.img` flash dumps generated by embedded devices running UFFS. It was specifically designed to bridge the gap between **Big-Endian flash images** (such as those generated by AVR32 microcontrollers) and **Little-Endian host machines** (like 64-bit Intel/Apple Silicon Macs and standard PCs).

## Repository Structure
```
.
├── bridge/         # FUSE bridge implementation (uffs-fuse.c) 
└── vendor/uffs/    # Patched UFFS core library
```

## Build Instructions
This project uses CMake to automatically detect your host's architecture and link the necessary FUSE libraries.

### 1. Clone the repository
```bash
git clone https://github.com/LSinus/uffs-fuse
cd uffs-fuse
```

### 2. Create a build directory
```bash
mkdir build && cd build
```

### 3. Configure the build
By default, the project assumes your target flash image is Big-Endian (like the AVR32 embedded environment):
```bash
cmake ..
```

> **Note:** If you are mounting a flash image created by a standard Little-Endian CPU (like an ARM Cortex-M), disable the Big-Endian flag:
> ```bash
> cmake -DFLASH_IS_BIG_ENDIAN=OFF ..
> ```

### 4. Compile
```bash
make
```

This will generate the `uffs-fuse` executable and the dynamically linked `libuffs_shared` library in your `build/` directory.

## Usage

### Mounting
Provide the path to your `.img` file and an empty mount point directory:

Assume to use an image called flash0 that is mounted on the embedded system at /flash0/
```bash
mkdir -p mnt/flash0
./uffs-fuse ./flash.img mnt/flash0
```

### Verifying the Mount
After mounting, confirm the filesystem is accessible by listing its contents:
```bash
ls mnt/flash0
```
You should see the files and directories from your flash image. If the directory appears empty when you expect files, double-check your flash geometry settings (see [Configuration](#configuration)) — incorrect `total_blocks` or `page_data_size` values are the most common cause.

### Unmounting
```bash
# macOS
umount mnt/flash0

# Linux
fusermount -u mnt/flash0
```

### Configuration
You can easily set the flash geometry by modifying the `setup_storage` function in `uffs-fuse.c`:

```c
static void setup_storage(struct uffs_StorageAttrSt *attr)
{
    attr->total_blocks = your_flash_total_blocks;       // Total number of erase blocks on the device
    attr->page_data_size = your_flash_page_data_size;   // Usable bytes per page (e.g. 512, 2048)
    attr->pages_per_block = your_flash_pages_per_block; // Number of pages in each erase block (e.g. 32, 64)
    attr->spare_size = your_flash_spare_size;           // OOB/spare area bytes per page (e.g. 16 for 512-byte pages)
    attr->block_status_offs = your_flash_block_status_offset; // Byte offset in spare area used for bad-block marking
    attr->ecc_opt = UFFS_ECC_SOFT | UFFS_ECC_NONE | UFFS_ECC_HW | UFFS_ECC_HW_AUTO;
    attr->layout_opt = UFFS_LAYOUT_UFFS;
}
```

These values must match the physical geometry of your flash chip. You can typically find them in:
- Your device's datasheet
- The UFFS initialization code in your embedded firmware
- The flash driver configuration (`uffs_FlashOps` struct)

If your flash image is mounted at a different path on the embedded target, update the mount point to match:
```c
#define MOUNT_POINT "your_mount_point"  // e.g. "/flash0" or "/data"
```

## macOS Tips & Known Issues
When copying files from your Mac into the mounted FUSE filesystem via the terminal, macOS will attempt to copy extended attributes and permissions that UFFS does not support. While the FUSE bridge safely ignores these, `cp` may throw a `Function not implemented` or `Operation not permitted` warning.

To silence this and copy cleanly, use the `-X` flag (do not copy extended attributes):
```bash
cp -X my_firmware.bin mnt/flash0/
```
